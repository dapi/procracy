# PRocracy — Product Requirements Document

## 1. Обзор продукта

**PRocracy** — issue bounty platform с GitHub-ботом. Спонсоры финансируют решение конкретных issues в open source проектах, разработчики берутся за задачи с залогом и дедлайном, выплата происходит автоматически при мерже PR.

### Проблема

Open source проекты накапливают сотни нерешённых issues. У мейнтейнеров нет ресурсов, у разработчиков нет мотивации. Существующие платформы (Algora — 23% комиссия, Polar.sh — bounty не в фокусе) не решают проблему commitment: кто угодно "берёт" issue и бросает.

### Решение

Маркетплейс где:
- **Спонсоры** накидывают деньги на issues
- **Исполнители** берут issue, вносят **залог** и получают **дедлайн**
- PR merge → **автовыплата**
- Провал дедлайна → залог уходит на баланс проекта

### Ключевая дифференциация

| Фича | PRocracy | Algora | Polar.sh |
|---|---|---|---|
| Залог исполнителя | ✅ | ❌ | ❌ |
| Дедлайн с последствиями | ✅ | ❌ | ❌ |
| Комиссия | 20% | 23% | 5% |
| Фокус на bounty | ✅ | ✅ | Частично |

## 2. Пользователи и роли

### Спонсор
Любой человек или компания, заинтересованные в решении issue. Вносит деньги на баланс проекта или конкретной issue.

### Исполнитель (Developer)
Разработчик, который берётся за issue. Обязан:
- Заявить о намерении (claim)
- Внести залог
- Уложиться в дедлайн
- Открыть PR, решающий issue

### Мейнтейнер (Project Owner)
Владелец репозитория. Призывает бота, управляет проектом на платформе. Мержит PR.

## 3. User Flows

### Flow 1: Регистрация проекта

```
Мейнтейнер упоминает @procracy-bot в любом issue
→ Бот создаёт паспорт проекта на сервере
→ Бот отвечает в issue: "Проект зарегистрирован, ссылка на дашборд"
→ Проект появляется на публичном дашборде
→ Issue появляется в списке доступных задач
```

### Flow 2: Финансирование issue

```
Спонсор заходит на дашборд PRocracy
→ Находит проект или issue
→ Пополняет баланс issue (карта / крипто / другое)
→ Сумма отображается на бейдже issue в GitHub
→ Бот комментирует в issue: "Баунти: $XXX"
```

### Flow 3: Claim issue (исполнитель берёт задачу)

```
Исполнитель видит issue с баунти
→ Комментирует: "@procracy-bot claim"
→ Бот отвечает: "Для claim нужно внести залог $YY и выбрать дедлайн"
→ Исполнитель вносит залог на платформе и выбирает срок
→ Бот комментирует: "Issue закреплена за @developer, дедлайн: DD.MM.YYYY"
→ Issue помечается как "in progress"
```

### Flow 4: Успешное завершение

```
Исполнитель открывает PR, ссылается на issue
→ Мейнтейнер мержит PR
→ GitHub webhook → сервер PRocracy
→ Автовыплата: баунти - 20% комиссия → исполнителю
→ Залог возвращается исполнителю
→ Бот комментирует: "Выплачено $XXX за решение #123"
```

### Flow 5: Провал дедлайна

```
Дедлайн наступил, PR не вмержен
→ Бот комментирует: "Дедлайн истёк. Залог $YY переведён на баланс проекта"
→ Залог → баланс проекта (для будущих выплат)
→ Issue снова доступна для claim другим исполнителем
→ Накопленный баунти сохраняется
```

## 4. Функциональные требования

### 4.1 GitHub Bot (GitHub App)

- **Триггер регистрации**: упоминание `@procracy-bot` в issue
- **Команды в комментариях**:
  - `@procracy-bot claim` — взять issue
  - `@procracy-bot unclaim` — отказаться (до дедлайна, залог возвращается)
  - `@procracy-bot status` — текущий статус issue/проекта
  - `@procracy-bot fund $XXX` — ссылка для пополнения баунти
- **Автоматические действия**:
  - Реакция на PR merge (webhook) → автовыплата
  - Мониторинг дедлайнов → предупреждение за 24ч, конфискация залога
  - Обновление бейджей с суммой баунти
- **Комментарии бота**: информативные, со ссылками на дашборд

### 4.2 Бэкенд / API

**Сущности:**

```
Project (паспорт проекта)
├── github_repo: string (owner/repo)
├── balance: decimal (общий баланс проекта)
├── registered_at: timestamp
└── issues: Issue[]

Issue
├── github_issue_id: number
├── project_id: FK
├── bounty: decimal (накопленная сумма)
├── status: open | claimed | completed | expired
├── claimed_by: User | null
├── deposit: decimal (залог)
├── deadline: timestamp | null
└── funding_history: FundingEvent[]

User
├── github_username: string
├── balance: decimal (кошелёк на платформе)
├── reputation: number
└── completed_issues: number

FundingEvent
├── user_id: FK (спонсор)
├── issue_id: FK
├── amount: decimal
└── created_at: timestamp

Payment
├── issue_id: FK
├── recipient_id: FK (исполнитель)
├── amount: decimal (баунти - комиссия)
├── commission: decimal (20%)
├── deposit_returned: decimal
└── paid_at: timestamp
```

### 4.3 Веб-дашборд

**Публичные страницы:**
- Каталог проектов, ищущих спонсоров
- Список issues с баунти (сортировка по сумме, языку, сложности)
- Профиль проекта: баланс, активные issues, история выплат
- Профиль исполнителя: репутация, выполненные задачи

**Личный кабинет:**
- Баланс кошелька (пополнение / вывод)
- Мои claims: активные, завершённые, просроченные
- История транзакций

### 4.4 Платежи

- Пополнение баланса: Stripe (карты), крипто (опционально в v2)
- Выплаты: Stripe Connect / банковский перевод
- Внутренние переводы: мгновенные (баланс → залог, баунти → кошелёк)
- Комиссия: 20% от суммы баунти при выплате

## 5. Механика залога

### Размер залога
Вариант: фиксированный % от баунти (например, 10-20%). Исполнитель видит сумму залога до claim.

### Дедлайн
Исполнитель сам выбирает дедлайн из предложенных вариантов (7 / 14 / 30 дней) или указывает свой. Мейнтейнер может установить максимальный допустимый срок.

### Конфискация
- Дедлайн истёк, PR не вмержен → залог переводится на баланс проекта
- Исполнитель может `unclaim` до дедлайна → залог возвращается
- PR вмержен → залог возвращается + выплата баунти

### Защита от злоупотреблений
- Мейнтейнер не может мержить свой PR на свою же issue (или может, но без выплаты)
- Один исполнитель на issue в момент времени
- Минимальный баунти для claim (чтобы залог имел смысл)
- Репутация влияет на доступ к крупным задачам

## 6. Бизнес-модель

| Источник дохода | Описание |
|---|---|
| Комиссия 20% | От каждой выплаты баунти |
| Конфискованные залоги | Идут на баланс проекта, не сервису |

### Юнит-экономика (пример)

```
Спонсор вносит:           $100
Баунти на issue:          $100
Исполнитель вносит залог: $15 (15%)
PR вмержен:
  → Исполнитель получает:  $80 (баунти - 20%)
  → PRocracy получает:     $20 (комиссия)
  → Залог возвращается:    $15
```

## 7. MVP Scope (v1)

### Включено
- [ ] GitHub App: регистрация проекта через упоминание
- [ ] GitHub App: команды claim / unclaim / status
- [ ] Webhook: PR merge → автовыплата
- [ ] Бэкенд: проекты, issues, пользователи, балансы
- [ ] Дашборд: каталог проектов и issues с баунти
- [ ] Дашборд: профиль пользователя, баланс
- [ ] Платежи: пополнение через Stripe
- [ ] Платежи: выплаты через Stripe Connect
- [ ] Механика залога и дедлайнов
- [ ] Бот-уведомления в GitHub (комментарии)

### Отложено (v2+)
- Крипто-платежи
- Репутационная система с рейтингом
- API для сторонних интеграций
- Множественные claim (конкурс решений)
- Квадратичное финансирование (идея Gitcoin)
- Интеграция с другими платформами (GitLab, Bitbucket)
- AI-оценка сложности issue

## 10. Риски

| Риск | Митигация |
|---|---|
| Мейнтейнер не мержит хороший PR | Арбитраж / таймаут на ревью |
| Спам-claims ради блокировки issue | Залог отсекает несерьёзных |
| Низкое качество PR | Репутация + мейнтейнер решает мержить или нет |
| Мейнтейнер мержит свои PR | Запрет или фильтр self-merge |
| Отмывание денег | KYC для выплат выше порога |
| Конкуренция с Polar.sh (5%) | Фокус на commitment-механику (залог), не на цену |
